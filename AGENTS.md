# AGENTS.md

## Scope

This repository is a macOS app with a thin Xcode host and a Swift Package that contains almost all product logic.

- App host: `CineFlow/`
- Xcode project: `CineFlow.xcodeproj`
- Core package: `SharedApp/`
- Primary business target: `SharedApp/Sources/Shared`

Agents working in this repository should treat `SharedApp` as the default place for product logic, UI, state, networking, and player integration.

## Repository Map

- `CineFlow/CineFlowApp.swift`
  The macOS app entry point. Keep the host thin.
- `SharedApp/Package.swift`
  The package manifest and dependency source of truth.
- `SharedApp/Sources/Shared/UI/Main`
  Main product UI and feature flows.
- `SharedApp/Sources/Shared/Model`
  SwiftData models and local persistence-facing types.
- `SharedApp/Sources/Shared/Network`
  API wrappers, transports, and shared networking utilities.
- `SharedApp/Sources/Shared/Support`
  Shared support code, including player backend integration.
- `SharedApp/Sources/RemoteMediaLibrary`
  OpenAPI source inputs for the remote media library API.
- `SharedApp/Sources/DandanApi`
  OpenAPI source inputs for DanDan API.
- `SharedApp/Plugins/BuildPlugin`
  Build plugin logic.
- `SharedApp/Sources/SecretGenerator`
  Generates `Secrets.swift` from `secrets.env`.
- `CineFlowTests/`, `CineFlowUITests/`
  Test targets. Coverage is currently light, so build verification matters.

## Working Rules

- Default to modifying code in `SharedApp` unless the task is explicitly about the macOS host shell.
- Keep the app host thin. Do not move business logic into `CineFlow/` unless there is a platform-host reason.
- Preserve the existing feature structure. New feature work should follow the current `ContentView + Presenter` pattern used under `Shared/UI/Main`.
- Avoid broad refactors unless the task explicitly requires them.
- Do not silently rework unrelated files in a dirty worktree.

## Code Placement

- Feature UI belongs in `SharedApp/Sources/Shared/UI/Main/<Feature>`.
- Feature state, actions, reducer logic, navigation, and effects belong in the corresponding `*Presenter.swift`.
- Local model and persistence code belongs in `SharedApp/Sources/Shared/Model`.
- Shared networking code belongs in `SharedApp/Sources/Shared/Network`.
- Cross-feature helper code belongs in `SharedApp/Sources/Shared/Support`.
- Player abstractions and backend-specific player implementations belong in `SharedApp/Sources/Shared/Support`.
- Do not spread player-backend details across unrelated UI files.

## Player Rules

- The current player backend is `FSPlayer`.
- If player work expands, prefer introducing a backend-agnostic abstraction in `SharedApp/Sources/Shared/Support`.
- Keep backend-specific APIs isolated behind that support layer.
- Do not couple `UI/Main/Player` directly to a specific backend more than necessary.

## Generated Files And Secrets

- `SharedApp/secrets.env` is local-only and must never be committed.
- If a sample is needed, use a separate example file such as `secrets.env.example`.
- `Secrets.swift` is generated by the build plugin. Do not edit generated secret output by hand.
- OpenAPI-generated code should not be hand-maintained.
- When API schema changes are needed, edit:
  - `SharedApp/Sources/RemoteMediaLibrary/openapi.json`
  - `SharedApp/Sources/RemoteMediaLibrary/openapi-generator-config.yaml`
  - `SharedApp/Sources/DandanApi/openapi.json`
  - `SharedApp/Sources/DandanApi/openapi-generator-config.yaml`
- If package dependencies change, ensure the lockfile state is consistent with the manifest.

## Git Rules

- Every completed atomic change should be committed as its own commit.
- Keep each commit self-contained and focused on one coherent change.
- Do not combine unrelated cleanup with the requested work.
- If the worktree is already dirty, avoid touching unrelated modified files.
- Never revert user changes unless explicitly asked.

## UI And Design Rules

- Follow Apple's platform design language first.
- Use Apple HIG as the baseline, not generic cross-platform styling.
- For macOS UI, prefer native SwiftUI and AppKit behaviors, materials, spacing, and controls.
- Favor a liquid-glass direction where appropriate:
  - translucent materials
  - layered depth
  - blur and vibrancy
  - soft separators
  - restrained highlights
- Do not overuse effects if they reduce readability or contrast.
- Prioritize clarity, hierarchy, and native feel over novelty.
- When in doubt, choose the more Apple-like solution.

## Build And Verification

- This repository should be verified primarily as a macOS app.
- Prefer macOS builds over iOS-oriented checks unless the task explicitly targets another platform.
- After meaningful changes, run a macOS build for verification.
- Treat build success as the minimum verification bar.
- Because automated test coverage is currently sparse, do not claim high confidence without build verification.

## Dependency Notes

- `SharedApp/Package.swift` is the manifest source of truth.
- Keep package resolution consistent with the intended dependency version.
- If a package version is updated, verify that the resolved state and actual build both match the intended version.

## Agent Behavior

- Read the surrounding feature before editing.
- Keep changes minimal and local.
- Prefer consistency with existing patterns over introducing a new pattern.
- Call out uncertainty before making risky structural changes.
- If a task suggests a larger architectural move, propose the boundary first, then implement after alignment.
